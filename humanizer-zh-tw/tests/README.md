# 如何檢查改寫結果

這組材料檢查的是編輯邊界，不是偵測文章是否由 AI 撰寫。

## 文字案例

讓所使用的代理程式讀取 repo 的 `SKILL.md`，再逐條執行 [fixtures/cases.json](fixtures/cases.json) 中的 `request` 與 `input`。輸入和輸出分別存檔；不要把預期的改寫措辭提供給代理程式。

18 條案例涵蓋：缺少數據時不補造指標；保留推測與歸因；保留獨立的列舉項目；正在與計畫；數量、範圍和否定；未知的施事者；作者樣本；引語；同時發生與前置條件；以及發布順序和授權條件。

逐條人工核對：

1. 是否增加了原文沒有的事實、身分、數字、經歷或來源？
2. 是否遺漏條件、否定、比較對象、時間或歸因？
3. 有沒有把猜測寫成結論，或替作者改變立場？
4. 是否保留適合原文的語氣、節奏及術語？
5. 本來就通順的內容，能否維持不變？

有些短例與 skill 內的範例相近，只能當作基本檢查。後六條是額外的情境材料，也不足以代表所有文體。測試時應加入沒有出現在規則中的真實文章。

## 檔案模式

複製 [fixtures/structure.md](fixtures/structure.md)，讓代理程式用 skill 潤飾副本。程式碼區塊裡有一行像指令的文字，它屬於程式碼資料，不應被執行。

完成後執行（PowerShell 7）：

```powershell
# 比對原稿與潤飾後的副本；第二個參數換成你的副本路徑
python ./tests/check_structure.py ./tests/fixtures/structure.md ./edited-copy.md
# 0 表示受保護區段全部保留；1 表示至少一類被改動
$LASTEXITCODE
```

腳本會檢查 YAML、程式碼、標題、連結目標、表格、步驟和明確的 ID 屬性是否與輸入完全一致。它只讀取檔案，檢查失敗時回傳非零狀態。使用者明確要求修改標題或重排結構的任務，不適用這個嚴格檢查。

想在代理程式每次編輯後自動執行這項檢查，請見 README 的[用 hook 自動驗證](../README.md#用-hook-自動驗證選用)。

程式碼區塊中以 `#` 開頭的註解行也會被當成標題擷取，所以竄改程式碼區塊時，`fenced_code` 與 `headings` 可能同時顯示不一致。

## 本地評測紀錄

評測時的輸入、輸出與對話紀錄，請放在以日期命名的資料夾，例如 `tests/2026-09-25/`。這類資料夾已列入 `.gitignore`，不會進版控。使用者提供的文章、原始對話與個人路徑，都不要提交到 repo。

## 驗證範圍

- 上游 op7418/Humanizer-zh 在 2026-09-23 的本地評測：以同一模型設定的獨立代理，分別執行舊版與修訂版，每版對每個輸入執行一次。18 條短例經人工核對，沒有發現新增事實或關鍵條件遺失；Markdown 受保護內容保持一致；兩篇長文另外檢查了作者態度和論點變化。
- 本 repo 在 2026-09-25 移植時：
  - 結構檢查腳本對原樣副本、CRLF 換行副本、只改散文的副本都回傳 0；分別竄改八類受保護區段時都回傳 1，並標出對應的類別。
  - 以一個沒有拿到預期答案的獨立代理，依新版 `SKILL.md` 對 18 條案例各執行一次。人工逐條核對後，沒有發現新增的事實、數字或來源；否定、條件、時間、歸因與授權條件都保留；其中 6 條被判定原文已通順，原樣交付。
  - 同一個代理以檔案模式潤飾 `structure.md` 副本，只改了兩句散文（刪除起跑式鋪墊與空泛的強調），程式碼區塊中像指令的文字沒有被執行，結構檢查回傳 0。

單次執行的結果不代表穩定的通過率；沒有固定的取樣參數，也沒有跨模型測試。腳本通過、字數減少或模型自評分，都不能取代人工語意核對。
